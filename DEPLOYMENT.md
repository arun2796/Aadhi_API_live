# DEPLOYMENT — API (`Aadhi_API_live`)

How the AadhiCrackers **API and its PostgreSQL database** reach production on one AWS Lightsail
instance, with product images on Cloudflare R2 and automatic deployment from GitHub.

This file covers the API only. The two frontends each have their own runbook:
`Aadhi_UI_live/customer-web/DEPLOYMENT.md` and `Aadhi_UI_live/admin-web/DEPLOYMENT.md`.

```
              ┌──────────────────────────────────────────────┐
   frontends ─▶  nginx :443 ──proxy──▶ Kestrel :5000          │  AWS Lightsail
   (Pages)    │                            │                  │  one Ubuntu instance
              │                            ▼                  │  static IP
              │                    PostgreSQL :5432           │
              │                    (localhost only)           │
              └───────┬──────────────────────┬───────────────┘
                      │ uploads/serves       │ verifies Google ID tokens
                      ▼                      ▼
               Cloudflare R2           Firebase / Google
               bucket: aadhicrackers   project: aadhi-crackers
```

No Docker. The API is published **self-contained** by CI, so the server needs no .NET runtime —
a release is a directory you can run, and five of them stay on disk for instant rollback.

---

## 1. The Lightsail instance

**Already have one with a static IP and PostgreSQL installed?** Run the checks at the end of
this section, then continue — the provision script only fills in what is missing.

From scratch: Lightsail console → **Create instance** → Linux/Unix → **OS Only →
Ubuntu 24.04 LTS**, size **2 GB RAM / 2 vCPU minimum** (512 MB OOMs running PostgreSQL and the
API together). **Networking → Create static IP** and attach it — without one the address
changes on stop/start and DNS breaks.

**Lightsail console firewall** (Networking → IPv4 Firewall) — allow only SSH 22, HTTP 80,
HTTPS 443. Never 5432: the database is reached over an SSH tunnel (§8).

**DNS:** `A` record `api.aadhicracker.in` → the static IP.

Checks on an existing instance:

```bash
free -m                                   # 2 GB+ total
systemctl is-active postgresql            # active
sudo -u postgres psql -tAc 'SHOW server_version'
df -h /                                   # a release is ~120 MB, five are kept
```

## 2. Provision (once)

```bash
ssh ubuntu@<static-ip>
git clone https://github.com/arun2796/Aadhi_API_live.git /tmp/aadhi
sudo bash /tmp/aadhi/deploy/provision-lightsail.sh
```

Idempotent — re-running never clobbers an existing database or environment file. Installs
PostgreSQL, nginx, certbot, ufw, fail2ban; creates the `aadhi` service account, the
`aadhicrackers` database and role, release directories, the systemd unit,
`/etc/aadhi-api/aadhi-api.env`, and the nightly backup cron.

**It prints the generated database password exactly once — save it.**

## 3. The environment file — every runtime secret lives here

```bash
sudo nano /etc/aadhi-api/aadhi-api.env
sudo systemctl restart aadhi-api          # after any edit; no redeploy needed
```

Root-owned, 0600, never part of a release, never in git, never in GitHub — a compromised
GitHub account cannot read your database password, and rotating a credential needs no code
change. Full annotated reference: [`deploy/aadhi-api.env.example`](deploy/aadhi-api.env.example).
What must be real before first boot:

| Key | Value |
|---|---|
| `ConnectionStrings__DefaultConnection` | `Host=localhost;Port=5432;Database=aadhicrackers;Username=aadhi;Password=<from §2>` |
| `JwtSettings__SecretKey` | generated by the provision script; rotate with `openssl rand -base64 48` (signs everyone out) |
| `Cors__AllowedOrigins` | `https://aadhicracker.in;https://www.aadhicracker.in;https://adminerp.aadhicracker.in` — exact scheme, no trailing slash; one character off and browsers block every frontend call |
| `Storage__Provider` + 5 × `Storage__R2__*` | §5 |
| `Firebase__ProjectId` | `aadhi-crackers` — §6 |
| `Seeding__IncludeDemoData` | **`false`**, or demo products/customers/orders are seeded into the live database on first boot |
| `Seeding__AdminEmail` / `Seeding__AdminPassword` | the initial admin login; change the password in the app afterwards |

The API **refuses to start** — naming the exact key — on a blank connection string, blank R2
values while `Provider=R2`, or a missing/short/default JWT secret. A restart-loop right after a
deploy means a missing key: `journalctl -u aadhi-api -n 50` says which.

## 4. TLS

```bash
sudo nano /etc/nginx/sites-available/aadhi-api     # replace api.aadhicracker.in
sudo ln -sf /etc/nginx/sites-available/aadhi-api /etc/nginx/sites-enabled/aadhi-api
sudo rm -f /etc/nginx/sites-enabled/default
sudo certbot --nginx -d api.aadhicracker.in
sudo nginx -t && sudo systemctl reload nginx
```

certbot installs its own renewal timer. The 443 block references certificate files that do not
exist until certbot runs — if `nginx -t` fails first, comment the block out, run certbot,
uncomment.

## 5. Cloudflare R2 — product images

Images upload through `POST /api/v1/uploads/image` into R2 and are served to browsers straight
from R2 — never through this server, never from its disk (each deploy replaces the release
directory).

1. **Bucket:** R2 → Create bucket → `aadhicrackers`.
2. **Token:** R2 → Manage R2 API Tokens → Create — permission **Object Read & Write**, scoped
   to **this bucket only**. The Access Key ID / Secret are shown once; they go in the env file
   (§3) and nowhere else — only this server talks to R2.
3. **Public serving:** bucket → Settings → **Public access** → allow the r2.dev subdomain
   (`https://pub-<hash>.r2.dev`), or better, connect a **custom domain**
   (`images.aadhicracker.in`) — r2.dev is rate-limited and meant for development.
4. Env keys: `Storage__Provider=R2`, `AccountId` (32-hex, dashboard sidebar), `AccessKeyId`,
   `SecretAccessKey`, `BucketName=aadhicrackers`, `PublicBaseUrl` = the serving origin from
   step 3. **Never the `…r2.cloudflarestorage.com` S3 endpoint** — that host requires signed
   requests, so every image would 401 in the browser.

Verify after boot: the log prints
`🗄️ Image storage: Cloudflare R2 — bucket 'aadhicrackers' …`; upload a product photo from the
admin and open its URL in an incognito tab.

## 6. Firebase — server side of Google sign-in

The storefront posts Google ID tokens to `POST /api/v1/auth/firebase-login`. This API verifies
them cryptographically against Google's published keys — signature, issuer, audience, expiry,
RS256 only — and takes identity exclusively from verified claims. A verified new user becomes a
**Customer**; a staff email via Google is refused, so social login can never reach the admin.

Server configuration is one non-secret value in the env file:

```
Firebase__ProjectId=aadhi-crackers
```

It must match the frontend's `projectId` (`customer-web/src/services/firebase.ts`) — the token's
issuer and audience are validated against it, so a mismatch rejects every Google sign-in with
"Invalid or expired Firebase credentials". No Admin SDK, no service-account JSON, no Firebase
secret exists anywhere in this system.

The Firebase **console** steps (enabling the Google provider, authorized domains) live with the
app that uses them: `customer-web/DEPLOYMENT.md` §4.

## 7. CI/CD

| Workflow | Trigger | Pipeline |
|---|---|---|
| `ci.yml` | every branch except `ak-dev`, PRs | build → test → EF model-drift check |
| `deploy-api.yml` | push to `ak-dev` (the working branch), or Run workflow | preflight (secrets, key shape) → build → **test gate** → self-contained publish → rsync to `releases/<sha>` → activate: flip symlink, restart, poll `/health/ready`, **automatic rollback** on failure → public smoke test |

Repository → Settings → Secrets and variables → Actions:

| Kind | Name | Value |
|---|---|---|
| secret | `LIGHTSAIL_HOST` | the static IP, or `api.aadhicracker.in` |
| secret | `LIGHTSAIL_USER` | `ubuntu` |
| secret | `LIGHTSAIL_SSH_KEY` | private deploy key, `BEGIN`/`END` lines included |
| variable | `API_PUBLIC_URL` | `https://api.aadhicracker.in` — enables the post-deploy public smoke test |

Deploy key (dedicated and revocable — not your personal key):

```bash
ssh-keygen -t ed25519 -f deploy_key -C "github-actions" -N ""
ssh-copy-id -i deploy_key.pub ubuntu@<static-ip>
ssh -i deploy_key ubuntu@<static-ip> 'echo ok'    # confirm BEFORE pasting
# paste deploy_key (private, in full) into LIGHTSAIL_SSH_KEY, then:
rm deploy_key deploy_key.pub
```

Tests are the only gate between a push to `ak-dev` and production. Per-error troubleshooting for
every job: [docs/GITHUB_ACTIONS.md](docs/GITHUB_ACTIONS.md).

## 8. Database: access and backups

The database starts empty — EF migrations build the whole schema on first boot, each one
logged. `listen_addresses` stays `localhost`; that is what keeps it off the internet.

**From your laptop** — SSH tunnel, nothing exposed:

```bash
ssh -L 5432:localhost:5432 ubuntu@<static-ip>
psql "host=localhost port=5432 dbname=aadhicrackers user=aadhi"
```

**A tool that cannot tunnel:** `sudo bash deploy/enable-remote-postgres.sh <your-ip>/32` —
TLS-only, one address, one database, one role; refuses `0.0.0.0/0`; undo with `--disable`.
Also open 5432 **restricted to that IP** in the Lightsail console firewall — it is a second,
separate gate.

**Backups:** nightly cron at 21:00 UTC — dump → gzip → `/var/backups/aadhi/` → **off-site copy
into the R2 bucket** under `db-backups/`. Restores, fetching from R2, and a restore drill:
[RESTORE.md](RESTORE.md). Enable Lightsail automatic snapshots too.

## 9. Verification checklist

- [ ] `curl -s https://api.aadhicracker.in/health/ready` → healthy, valid TLS
- [ ] `journalctl -u aadhi-api -n 40`: migrations applied, `Image storage: Cloudflare R2`,
      no CORS/JWT warnings
- [ ] Fresh DB has schema: `sudo -u postgres psql -d aadhicrackers -c 'SELECT count(*) FROM "Products";'`
- [ ] No demo data (products list empty on a fresh boot)
- [ ] Admin image upload lands in R2 and the URL serves publicly (incognito tab)
- [ ] Test order with payment screenshot → order's proof URL is `…/payment-proofs/…`, not `data:`
- [ ] Google sign-in from the storefront creates a Customer; a staff email is refused
- [ ] Push to any feature branch → `CI` green; push to `ak-dev` → deploy green, rollback log shows 5 releases kept
- [ ] Next morning: `/var/backups/aadhi/` has a dump AND the R2 bucket has `db-backups/…`
      (or run `sudo /usr/local/bin/aadhi-backup-database` now)

## 10. Operations

```bash
sudo systemctl status aadhi-api            # running?
journalctl -u aadhi-api -f                 # live logs
sudo systemctl restart aadhi-api           # after env edits
curl -s localhost:5000/health/ready        # health, on the box

ls -1t /var/www/aadhi-api/releases         # manual rollback: newest first
bash /tmp/deploy-release.sh <older-sha>    # same health check, same safety
```

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Restart-loop after deploy | Missing env key — the API refuses to start rather than run misconfigured; `journalctl -u aadhi-api -n 50` names it |
| 502 from nginx | Kestrel not listening — `ASPNETCORE_URLS=http://127.0.0.1:5000`, `systemctl status aadhi-api` |
| Frontends CORS-blocked | Origin missing from `Cors__AllowedOrigins` or differs by scheme/trailing slash |
| Images 404 | `PublicBaseUrl` is the S3 endpoint instead of the public origin, or r2.dev access is off |
| Image upload 500 | R2 credentials/account id wrong — the API error names the failing check |
| Google sign-in "Invalid or expired Firebase credentials" | `Firebase__ProjectId` ≠ frontend `projectId`, or `securetoken.google.com` unreachable |
| Deploy fails at Upload release | Key not authorized, or deploy user not yet in the `aadhi` group — log out/in once |
| Deploy "did not become healthy" | Release failed and was **already rolled back**; job log carries the last 60 service log lines |
| Backup log: "exists ONLY on this instance" | R2 keys missing from the env file — the off-site copy is the half that matters |
| psql to static IP refused / `no pg_hba.conf entry` | Remote access not enabled, or your IP changed — re-run `enable-remote-postgres.sh`, or use the tunnel |
